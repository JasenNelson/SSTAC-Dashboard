### 1.16 Tool-call batching discipline (anti-cascade) (2026-05-31, owner-requested)

**Problem (recurring across sessions):** one failed call in a PARALLEL tool batch CANCELS all its
siblings. A single bad command in a 20-call fan-out reads back as 19 "Cancelled: parallel tool call"
errors -- wasted tokens and a misleading transcript. Triggering incident 2026-05-31: a probe fleet
plus an inline ESM `import ... assert { type: 'json' }` (removed in Node 24) threw once and cancelled
the whole batch.

**Rules:**
- Batch in parallel ONLY independent calls you are confident will succeed (e.g. reading known
  files, git status). NEVER batch exploratory/probe calls whose failure modes are unknown -- run
  those ONE AT A TIME so a single failure does not waste the whole batch.
- Do NOT send "is the shell alive?" probe fleets. Empty output is usually SUCCESS, not a hang; do
  not re-run a command because it "returned no output." Do not sleep-and-retry to check liveness.
- Verify runtime/syntax BEFORE fanning out. Node JSON loading uses `fs.readFileSync` + `JSON.parse`
  (or `with { type: 'json' }` on Node 22+), NEVER the removed `assert { type: 'json' }`. Prefer a
  tiny `.cjs` helper over inline `-e` ESM with import attributes.
- When a command fails, diagnose the ONE failure and fix it before retrying; never re-issue the same
  batch verbatim. Look at the input (e.g. `head` the file) before writing a parser for an unknown
  encoding, rather than guessing a regex and burning calls on parse errors.
- Avoid unbounded/greedy `grep` regexes against large files (they can dump every line number);
  prefer the Grep tool with an anchored pattern.

**Memory anchor:** `[[cross-project-tool-call-batching-anti-cascade]]`.

# Codex Review

Policy revision: `2026-08-03-owner-review-activation-v1`.

Use `/codex-review` as a workflow, not as a synonym for a nested Codex CLI
command. Bind the review to an exact checkpoint, use independent evidence,
challenge disputed findings, and converge honestly before the guarded action.

## Activation

Classify each trigger exactly once.

### Ask once at an important decision or key milestone

Before crossing an important owner, architecture, governance, safety, scope,
sequencing, or release decision, or a key milestone, ask:

`This is a <trigger>. I recommend <mode>. Run /codex-review now: targeted, strategic, holistic, comprehensive/adversarial, or skip?`

Recommend the proportionate mode. Do not re-ask when `checkpoint_id`, mode,
and target hash are unchanged and the owner's answer is already recorded.

Key milestones include:

- before substantial or multi-hour implementation;
- a decision-ready plan, design, specification, or migration proposal;
- contract, schema, API, invariant, security, auth, data, or migration changes;
- phase or lane completion;
- PR or merge readiness;
- promotion, activation, deployment, or release gates; and
- material scope expansion or change to an approved plan.

### Run automatically

Run the effective project's prescribed review before commit. Do not ask the
owner to remember the gate. Also run without re-asking when the owner already
selected a review for the current checkpoint.

An owner opt-out is valid only when it is explicit, candidate-scoped, recorded,
and permitted by the effective project or workstream protocol. A stricter
project, protected-path, or system rule wins. If no opt-out path exists, cite
the controlling rule and stop. Never label an opt-out as GREEN.

### Skip the milestone prompt

Do not prompt strategically for ordinary status updates, routine test reruns,
mechanical evidence collection, or typo/comment/format-only work. At commit,
still follow the active project's review rule and never invent a trivial-change
exemption.

## Review modes

- `targeted`: Check one exact diff, artifact, finding, or fix for correctness,
  regressions, security, edge cases, tests, and acceptance criteria.
- `strategic`: Check intent, alternatives, sequencing, dependencies, owner
  gates, proportionality, and whether the proposal solves the right problem.
- `holistic`: Give free rein across architecture, project alignment, callers,
  consumers, operational reality, maintainability, drift, and unknown-unknowns.
- `comprehensive/adversarial`: Run targeted, strategic, and holistic lenses in
  one coordinated initial review. Do not turn the four mode names into four
  repetitive mandatory invocations.

Use comprehensive/adversarial for cross-cutting architecture, governance,
safety, contract, scope, migration, or release decisions. Use a narrower mode
when it is sufficient.

## Role and checkpoint ownership

Create or reuse one checkpoint receipt containing:

- `checkpoint_id` and `review_id`;
- role and `review_coordinator`;
- repository and worktree identity;
- exact target identity and `target_hash`: immutable commit SHA or base/head
  pair; otherwise repository HEAD plus staged-index identity, unstaged diff
  hash, and hashes of reviewed untracked files as applicable; use artifact
  hashes for standalone files;
- review mode and trigger;
- status, open findings, eligible paths, and owner disposition.

Material target changes invalidate the prior verdict. Do not run the same mode
concurrently for the same checkpoint and target hash.

### Executor

The executor owns implementation, remediation, targeted pre-commit preparation,
and exact-path eligibility. When separate Mission Control owns an owner gate,
freeze the candidate, provide the evidence packet, and wait. Do not self-grant
the strategic or holistic gate.

### Mission Control

Mission Control remains read-only. It verifies evidence, coordinates or runs
the independent owner-gate review, adjudicates findings, and returns a bounded
correction packet. It does not apply fixes, stage, commit, or duplicate an
executor-owned review for the same `(checkpoint_id, mode, target_hash)`.

### Solo session

A solo session may coordinate review and implementation when its mission grants
both authorities. Keep review receipts and guarded actions distinct.

## Adversarial review loop

1. Ground the checkpoint.
   - Read applicable global, project, and workstream rules.
   - Verify live branch, HEAD, target paths, dirty state, and active-session
     boundaries when repository-backed.
   - Treat plans, handoffs, summaries, and prior verdicts as claims.

2. Run the selected review.
   - Use an independent reviewer when available and allowed.
   - Give a self-contained prompt with target paths/hashes, intent, constraints,
     role boundaries, and requested verdict.
   - Require findings first, severity, exact evidence, and a concrete fix or
     decision request.
   - In an active Codex app/API session, do not invoke nested `codex review` by
     default. Use local review, Codex subagents, Claude, Cursor, or another
     project-approved reviewer. Nested CLI review requires explicit authority
     and a proven safe invocation surface.

3. Triage every finding.
   - `agree-fix`: valid and in scope.
   - `agree-defer`: valid and outside scope, with destination and gating point.
   - `disagree`: counter with exact evidence.
   - `needs-owner`: policy, product, authority, or risk decision.
   - `withdrawn`: reviewer accepts that the finding does not hold.

   BLOCKER or IMPORTANT findings cannot be unilaterally deferred or relabeled.

4. Resolve under the owning role.
   - Executor fixes agreed findings.
   - Mission Control returns correction instructions and remains read-only.
   - Preserve unrelated user work and exact path scope.

5. Perform a ripple sweep after contract-level changes.
   - Search all callers, consumers, docs, fixtures, schemas, examples, tests,
     diagrams, and historical descriptions affected by the changed contract.
   - Update live references or mark historical text as superseded.
   - Re-review unresolved findings, the fix delta, and ripple-affected surfaces.

6. Reach mutual agreement.
   - Quote disputed findings and counter-evidence.
   - Ask the reviewer to `DEFEND`, `REVISE`, `SPLIT`, or `WITHDRAW`.
   - Accept a defense when the evidence changes the conclusion.
   - After two substantive defend/revise rounds on the same unresolved dispute,
     present both positions, severity, evidence, and a recommendation to the
     owner. Do not loop indefinitely.

7. Close honestly.
   - `GREEN`: all findings are fixed, withdrawn, or mutually accepted as
     non-blocking under the applicable protocol.
   - `YELLOW_OWNER_ACCEPTED`: the owner explicitly accepts named residual risk
     and the applicable protocol permits that disposition.
   - `BLOCKED_UNRESOLVED`: required review is unavailable, a material dispute
     remains, or a controlling gate is not satisfied.

Never call a missing reviewer, an owner skip, or an unresolved material finding
GREEN.

## Reviewer and evidence discipline

- Prefer direct file, diff, test, receipt, and live-state evidence.
- Verify claims that a reviewer or tool is unavailable before falling back.
- Use each reviewer as an adversarial partner, not an oracle.
- Do not silently accept, reject, fix, or ignore a finding.
- Do not expose secrets or send private code to an external reviewer without
  applicable authority.
- Follow project-specific reviewer, model, disclosure, and gate requirements.
- A review workflow may use a subagent without launching a nested Codex CLI.

## Commit and milestone closeout

Report:

- checkpoint and target identity;
- targeted, strategic, holistic, or comprehensive verdict;
- independent reviewer status;
- mutual-agreement status;
- findings fixed, withdrawn, deferred, or owner-accepted;
- residual risks and controlling project rule;
- verification performed;
- exact paths eligible for staging or the next guarded action.

Do not stage, commit, push, merge, promote, activate, deploy, or release unless
the effective project protocol and the checkpoint verdict permit it.
